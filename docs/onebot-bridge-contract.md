# OneBot LLM bridge v1 implementation contract

This is an optional project extension to OneBot v11, not part of that standard. The virtual protocol endpoint is Gensokyo-MCP; SeaDice and the reference NoneBot plugin are applications. Ordinary endpoints keep their existing behavior. No QQ account login or bind command is introduced.

## Wire protocol

OneBot message IDs and send acknowledgements use allocated positive int32 IDs, persisted and never reused while records are retained. Account/user/group IDs are JSON numbers (within the JavaScript safe integer range). In bridge mode a generated zero account defaults to the stable synthetic self ID 10000; valid configured IDs are retained, and an optional `ONEBOT_SELF_ID` override must be a positive safe integer. Login queries and inbound events use the same identity. This ID is a virtual protocol account, not a real QQ login. Authorization uses `Bearer` and reverse WS uses `X-Self-ID` and `X-Client-Role: Universal`.

The application calls `_llm_bridge_register` on every connection with `params: {version: 1, backend_instance: string, capabilities: ["reply", "complete"]}` and its ordinary action echo. Success data is `{version: 1, connection_id: string}`. Requests and their emitters are bound to this connection; reconnect never replays requests. The bridge publishes readiness only after writing the registration ACK on that socket. Applications must handle an immediately following event while their registration result is being consumed, without processing it under an unregistered or newer socket. Repeated registration on the same socket is rejected.

No custom inbound metadata is required: the source ID is the ordinary message event's message_id. The enabled dedicated SeaDice endpoint accepts bridge message events only on the authenticated socket whose registration succeeded. Its immutable request tracker captures that socket's returned connection_id and emitter. It must never read registration or emitter state from a later connection while sending.

Every output action contains a standard `reply` segment referencing the original virtual inbound `message_id` (including private outputs of group commands). Its `data.id` accepts the decimal string used by the [OneBot v11 message-segment specification](https://github.com/botuniverse/onebot-11/blob/master/message/segment.md#回复), as well as an integral JSON number; both must resolve to the same positive int32 source ID. Outer event and action IDs remain numeric. Only text plus this correlation segment are supported in v1. Correlation is stripped from collected content. The current connection and original message ID must match; missing/ambiguous reply IDs, wrong recipients and late outputs fail with an ordinary OneBot error ACK. Echo is returned unchanged for any JSON type.

The application calls `_llm_bridge_complete` with `params: {version: 1, source_message_id: int32, connection_id: string, status: "ok" | "failed", output_count: nonnegative integer}`. Complete only after all registered tasks and sends finish; output_count counts successful send ACKs across group/private sends. Completion and count mismatch fail closed. No quiet timer declares success. Standard send ACK means accepted by this virtual bridge, not delivered to QQ.

## Trusted MCP client

`call_ws` retains payload and target arguments, adding backend_id and request_id. Bot integration uses `{backend_id, request_id, payload, audience: "group" | "private", user_key, group_key?, group_role?}`; keys are trusted app-scoped opaque SDK identities, mapped persistently to virtual numeric IDs. The optional group_role is exactly owner/admin/member, injected by trusted code from the current raw QQ group event with matching sender/group IDs. Omission means unknown, not member. Private calls do not carry a group role. The bridge maps it to standard OneBot sender.role and includes it in the durable request fingerprint. Compatibility/test clients may supply user_id/group_id as safe positive integers or canonical decimal strings; the MCP boundary converts either form to numeric OneBot event IDs. Reject ambiguous mixed forms, fractions, exponents, signs, leading zeros and unsafe integers. request_id is generated by trusted code, never by the model.

Result in MCP text JSON: `{request_id, backend_id, audience, status: "ok" | "failed" | "unknown", outputs: [{action, audience, target_id, message}], private_receipt?: string, private_count?: number}`. For group audience, outputs contains only the requested group's public text; private content for the requester is stored separately. Other recipients are forbidden. For private audience, requester-private output may be returned as outputs. No raw errors or secret content in group results.

Authenticated internal endpoints (not model tools): `GET /internal/backends` returns `{backends:[{id,ready,version}]}`; `POST /internal/private/claim` body `{backend_id,request_id,receipt}` returns `{delivery_id,outputs:[{target_id,message}]}`; `POST /internal/private/ack` body `{delivery_id,status:"sent"|"failed"|"unknown"}`. Claim is atomic: a repeated claim cannot trigger another delivery. API statuses must be bounded and sanitized. Unknown delivery must not auto-retry. Private outbox TTL 10 min; final delivery removes plaintext. Request deduplication TTL 24 h; crash-interrupted dispatch becomes unknown. Store uses bbolt.

Environment for the bridge: `LLM_BRIDGE_ENABLED`, `LLM_BRIDGE_DATA_DIR`, `LLM_BRIDGE_MCP_TOKEN`, `LLM_BRIDGE_INTERNAL_TOKEN`, `ONEBOT_WS_TOKEN`. Configuration backend IDs remain deployment-defined and explicit. Queue limit 20 waiting per backend, execution deadline 30 seconds, at most 64 outputs and 128 KiB aggregate text. Unknown states are not retried automatically. Fresh registration fences old connection work.

`backend_instance` identifies one application process and stays unchanged across its socket reconnects. Persist a `queued` state before enqueueing and a `dispatching` state before any event write. An uncertain dispatched task quarantines that backend instance, because it may still mutate native game state after the MCP caller stops waiting. Only an exact completion from the original socket, connection, source ID and accepted output count can prove it drained; this never changes the cached unknown result or releases private content. Alternatively, a newly started application process registers a different instance ID. A reconnect of the same undrained instance cannot restore readiness. Bridge restart reconstructs quarantine from dispatched work; queued work becomes unknown without replay. Request TTL does not clear quarantine.

## qq-bot

Environment: `QQBOT_ONEBOT_ENABLED=false`, `QQBOT_ONEBOT_MCP_URL`, `QQBOT_ONEBOT_MCP_TOKEN`, `QQBOT_ONEBOT_INTERNAL_TOKEN`, `QQBOT_ONEBOT_BACKENDS=sealdice`, `QQBOT_ONEBOT_HIDDEN_ENABLED=false`. Tool `qqbot_onebot_command` arguments only `{requestId,backend,command}`. Dedicated trusted wrapper injects per-original-message identity and generates invocation IDs. No generic MCP tool exposure.

Only real current original messages authorize calls. Identities are immutable per-message SDK snapshots. One line, max 4000 chars. QQ routing/tool and SeaDice parsed guards share the documented command policy: native core and own-card writes, bounded roll/chargen commands, restricted read-only queries and native entertainment. Hidden aliases, delegation, scripts, arbitrary sends and unlisted operations are rejected. Master commands require an exact original private command, configured stable SDK identity and negotiated connection ACL. Disabling the optional integration hides its tool and does not require service access.

Repeated identical commands under the same original authorization share a trusted invocation ID and result, including simultaneous tool calls. Different commands under one original authorization run sequentially through private delivery and its acknowledgement; queued commands recheck eligibility and the original authorization before dispatch. A dispatched unknown result or failed/unknown hidden delivery blocks further commands under that original message for the rest of the turn. A new real QQ message creates fresh authorization; multiple intended rolls should use the native multi-roll expression. The private delivery test path uses a dedicated SDK REST client and sanitized logging, without mutating the ordinary chat sender's logger or forwarding private bodies to shared message hooks. The outer delivery deadline yields an unknown terminal state; it cannot cancel a request already sent by SDK 1.0.4, which does not accept the turn's AbortSignal and may continue reading a response body after its header timeout. Production hidden rolls remain blocked; future enablement requires verifying cancellation and response-body bounds as well as platform permission.

Tencent's official message documentation states that proactive push was discontinued on 2025-04-21. The production QQ SDK deployment therefore rejects group hidden rolls before backend execution, even if its hidden switch is true. The SDK exposes a C2C REST method, but that method's existence is not a platform capability proof. Do not substitute group message IDs, stale friend events or a bind workflow. Injected verified test transports may exercise the private outbox and sender isolation; they do not prove real QQ delivery. SDK friend/reject/receive events are tracked only from raw trusted events, with exact app-scoped identity checks. Reopening production requires a revised platform contract and actual delivery evidence.

The supplied SeaDice bootstrap uses a dedicated default Dice and data volume. Fresh data disables scripts, custom replies and unverified background extensions before initialization. Existing data is reused only if it has no unrelated endpoint and the same restricted configuration; otherwise startup fails without rewriting that data. Disabling the bridge environment preserves ordinary SeaDice startup.

## Optional group role capability

`group-role-v1` advertises per-request group role enforcement. The role travels in standard OneBot sender.role; the capability negotiation is an additive project contract. Gensokyo requires the current backend connection to support this capability for any nonempty group_role request, including at dispatch; this fences stale client probes after a backend downgrade. Legacy no-role calls remain compatible for diagnostics. SeaDice captures the role in its connection-bound request tracker before clearing ordinary player privileges. Before group activation and again before the native solver, group-wide rule writes require owner/admin on the original registered connection; member, unknown and private contexts are denied. Queries and own-card writes remain ordinary-player commands, and no group role grants Master or global trust. qq-bot independently checks the captured role, the exact native command in that owner's original message, and negotiated backend capability before dispatch. An unrelated owner's message in a merged batch cannot authorize another member's write. Unsupported backends retain ordinary commands but cannot receive group-wide writes from this wrapper. No environment switch disables this protection.

Gensokyo owner: its submodule, reference NoneBot plugin and protocol tests, bridge Docker/CI. SeaDice owner: its submodule, bridge endpoint configuration/execution tracking, Docker/CI. Bot owner: defaults/qqbot-onebot*.mjs, native registration/guard integration and targeted tests. Root: docs, compose/env/readme/Docker packaging, integration harness, review, submodule Git operations/releases. Agents do not commit/push until reviewed.

## Optional Master ACL capability

`master-acl-v1` is an additive project capability, not OneBot v11. When requested in `_llm_bridge_register`, Gensokyo returns `authorization: {"version":1,"master_user_ids":[...]}`. The ACL is bound to the current connection. Missing capability/data denies administration while ordinary reply/complete commands remain compatible. `/internal/backends` exposes negotiated capability strings, never source keys or privileged tool parameters.

`LLM_BRIDGE_MASTER_USER_KEYS` is a JSON string array of `appId:SDKopenid`, supplied from `QQBOT_ONEBOT_MASTER_USERS` in Compose. Max 100 entries; app ID 1–20 digits and SDK identity 1–128 ASCII letters/digits/underscore/hyphen. Empty is deny-all, malformed lists grant nothing, duplicates are deduplicated. Map keys via existing per-backend user identity allocation on registration; never treat an old numeric ID as authorization after a database reset. SeaDice validates private source IDs against this immutable ACL and keeps ordinary commands at player privilege. Native empty-master fallback, global trust and group roles cannot grant this bridge permission.
